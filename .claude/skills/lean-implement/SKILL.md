# lean-implement — 過剰設計を防ぐ実装ワークフロー

ベース: [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) の4原則。
このスキル全体を通して、次の4つを守る。

1. **考えてから書く** — 前提を明示する。不明点は推測せず質問する。解釈が複数あれば並べて選んでもらう。もっと単純な方法があれば提案して押し返す。
2. **シンプル第一** — 要求を満たす最小のコード。頼まれていない機能・設定項目・汎用化を入れない。一度しか使わないものを抽象化しない。起こり得ないケースのエラー処理を書かない。
3. **外科的な変更** — 触るのは必要な箇所だけ。隣のコードの「ついで改善」、壊れていないもののリファクタ、既存スタイルの変更をしない。自分の変更で不要になった import や関数は消す。既存のデッドコードは指摘だけして残す。
4. **ゴール駆動** — 作業を検証可能なゴール（=テスト）に変換し、通るまで回す。

**判定テスト:** 変更したすべての行が、承認された要求か設計に直接たどれること。シニアエンジニアが「やりすぎ」と言いそうなら削る。

## Step 0. 規模の判定（トリアージ）

プロセス自体が過剰にならないよう、最初に規模を判定してユーザーに伝える。

| 規模 | 目安 | 進め方 |
|---|---|---|
| S | 1ファイル・数十行以内、外部から見た挙動や公開 I/F が変わらない | Step 1 → Step 7 → Step 8（設計書・モックは省略） |
| M | 数ファイル、1レイヤー内に収まる、新規依存なし | 設計書は「設計メモ」（テンプレートの必須欄だけ）で良い |
| L | 複数レイヤー、ドメインモデル・DBスキーマ・依存関係・Docker/CI の変更、UI の新規画面 | 全ステップ |

判定に迷ったら大きい方を選ぶ。ユーザーが規模を指定した場合はそれに従う。

## Step 1. 要求の確認

1. 関係しそうなコードを読み、現状を把握する（読む範囲は必要最小限）。
2. 次をチャットで短く提示する。
   - ゴール（1〜2文）と**成功条件**（テストで検証できる形）
   - 置いた前提
   - 曖昧な点 → 解釈候補を並べて質問（AskUserQuestion が使えれば使う）
3. 答えが出るまで先に進まない。

## Step 2. 設計の提案

`docs/design/YYYYMMDD-<slug>.md` を [templates/design.md](templates/design.md) から作る（M は必須欄のみ）。

必ず含めるもの:
- **やらないこと（Non-goals）** — 範囲を明示的に切る
- **より単純な代替案と、それを採らない理由**（採るなら設計を差し替える）
- 置き場所（どのレイヤー・どのモジュールか）と依存の向き
- 影響範囲（変更する既存ファイル・公開 I/F・スキーマ・設定）
- テスト計画（先に書いて **red になるテスト** の一覧）

## Step 3. 設計書のセルフレビュー

人に出す前に、次の観点で自分の設計を見直し、修正したうえで設計書の「セルフレビュー記録」に残す。

- [ ] 各コンポーネント・クラス・設定項目が要求のどれかに直接たどれる
- [ ] 新しい抽象（基底クラス・Protocol・汎用ヘルパー）は、**今**2か所以上で使うか、レイヤー境界のポート（外部I/Oの差し替え口）である
- [ ] 新規の依存ライブラリは、標準ライブラリや既存コードで代替できない理由がある
- [ ] オニオンアーキテクチャの依存方向（外→内のみ）を守っている
- [ ] 基盤（ドメインモデル・DBスキーマ・共通ユーティリティ・設定・Docker/CI）への変更は最小で、必要性が書いてある
- [ ] 元に戻しやすい（マイグレーションやデータ変換がある場合はロールバック手順がある）

## Step 4. ゲート①：設計の承認（人）

設計書のパスと要点（5行程度）を示し、**「承認 / 修正 / 却下」** を明示的に聞いて止まる。

- 「承認」と明確に返ってくるまで Step 5 以降に進まない。曖昧な返事（「いいかも」など）は確認し直す。
- 修正依頼 → Step 2 に戻る。
- 承認されたら設計書の `status` を `approved` にし、日付を記録する。

## Step 5. ゲート②：モックの承認（UI変更があるときだけ）

UI に変更がなければ「UI変更なしのためモックは省略」と伝えて Step 6 へ。

- **既存画面の変更**: 既存のコンポーネント・スタイルをそのまま流用し、差分が分かる形で作る（変更前後を並べる、変更箇所を示す）。
- **新規画面**: 既存のデザイン（色・余白・部品）に合わせた静的モック。固定データのみ。
- モックには API 接続・状態管理・ロジックを入れない。置き場所は `docs/design/<slug>/mock/`（本番コードに混ぜない）。
- 確認してもらい、ゲート①と同じく明示的な「承認」で次へ。承認後、設計書にモックのパスと承認日を記録する。

## Step 6. 実装計画（プランモード）

プランモードに入る（ユーザーに Shift+Tab での切り替えを依頼するか、使えるならプランモード用のツールを使う）。
設計はすでに承認済みなので、ここでは **設計を変えずに実装の手順だけ** を立てる。

- 小さなステップに分け、各ステップに「先に書くテスト」と「検証方法」を付ける
- 承認済み設計書・モックへの参照を付ける
- 計画中に設計の変更が必要だと分かったら、実装に進まず Step 4 に戻って再承認をもらう

プランが承認されたら実装に入る。

## Step 7. 実装（red → green → refactor）

各ステップで:

1. **red**: 成功条件を表すテストを書き、実行して **失敗することを確認**する。失敗理由が想定どおり（未実装・アサーション不一致）であることも見る。実行結果の要約を設計書の「実装ログ」に残す。
2. **green**: テストを通す最小のコードを書く。
3. **refactor**: 自分が書いた範囲だけを整える。既存コードには手を出さない。

補足:
- コミットするかはユーザーの指示に従う。コミットする場合は「テスト追加」と「実装」を別コミットにすると、二次レビューで red 先行を確認しやすい。
- 外部ネットワーク（クロール先サイト等）に依存するテストは書かない。記録済みのレスポンスやフィクスチャを使う。

## Step 8. セルフレビュー

### 機械チェック
プロジェクトにある設定に従って実行する（`uv.lock` があれば `uv run` を前に付ける）。

```bash
# backend (Python)
ruff format .          # フォーマット適用
ruff check .           # Lint（--fix は自分の変更箇所の問題に限って使う）
mypy .                 # 型チェック（設定があればその対象に従う）
pytest                 # テスト

# frontend（frontend/ で実行）
npx biome check --write .   # フォーマット・Lint・import 整列（安全な修正のみ）
npx biome ci .              # 書き換えなしで最終確認
npm run typecheck           # package.json にあれば（Biome は型チェックをしない）
npm test                    # package.json にあれば
```

`--unsafe` 付きの自動修正は使わない（挙動が変わる修正を含むため）。必要なら手で直す。

エラーが残っている状態で完了報告しない。既存コード由来の警告は直さず、件数だけ報告する。

### 目視チェック
- [ ] `git diff` の全行が承認済み設計に対応している（ついでの変更がない）
- [ ] デバッグ出力・コメントアウトしたコード・不要になった import/関数が残っていない
- [ ] 設計書の Non-goals に書いたことをやっていない
- [ ] 設計と実装がずれた箇所があれば、設計書を更新してずれを明記した

### 報告
次を短くまとめて終える。
- 変更ファイル一覧と各ファイルの変更理由（1行ずつ）
- 機械チェックの結果（pass/fail）
- 設計からの逸脱（あれば）
- 次の一手: 「`/second-review` で二次レビューを実行してください」
