# second-review — 二次レビュー

あなたはこの変更を書いていないレビュアーとして振る舞う。
**ファイルを編集しない。** 実行してよいのは読み取り・検索・テスト/静的解析の実行・一時的な git worktree の作成だけ。
すべての指摘には根拠（ファイル:行、コマンド出力、設計書の該当箇所）を付ける。根拠を示せない指摘は書かない。

## Step 0. 対象の確定

1. 比較元を決める: `$ARGUMENTS` が指定されていればそれ、なければ `git merge-base HEAD main`（`main` がなければ `origin/main`、それもなければユーザーに確認）。
2. `git diff --stat <base>...HEAD` と、未コミットがあれば `git diff --stat` も取得し、対象ファイル一覧を作る。
3. 対応する設計書 `docs/design/*.md` を探して読む（slug・ブランチ名・変更ファイルから特定）。見つからなければ「設計書なし」として、要求はコミットメッセージやユーザーへの質問から把握する。
4. `CLAUDE.md` にレイヤー構成やレビュー規約があれば、下の既定値より優先する。

## Step 1. diff の確認

各 hunk について:
- [ ] 承認済み設計（または要求）に直接たどれる。たどれない変更（ついでのリファクタ・整形・命名変更）は指摘
- [ ] 設計書の Non-goals に入っていることをやっていない
- [ ] デバッグ出力、コメントアウトしたコード、TODO の置き去り、不要になった import が残っていない
- [ ] 秘密情報（APIキー・パスワード・トークン・個人の .env）が含まれていない
- [ ] 生成物・ロックファイルの変更が、依存の変更と整合している

## Step 2. オニオンアーキテクチャ

既定のレイヤー（CLAUDE.md の定義があればそちらを使う）:

| レイヤー | 例（クローラーの場合） | 依存してよい先 |
|---|---|---|
| domain | URL・ページ・クロール方針（robots 遵守、レート制限ルール、URL正規化）などのエンティティ/値オブジェクト/ドメインサービス | 標準ライブラリのみ |
| application | ユースケース（「サイトをクロールして保存する」）、ポート（Protocol/ABC）の定義 | domain |
| infrastructure | HTTPクライアント、HTMLパーサー、DB/ストレージ、ブラウザ自動化 | application, domain（ポートを実装する） |
| presentation | API ルーター、CLI、スケジューラのエントリポイント | application |

確認:
- [ ] 変更ファイルの import を調べ、内側から外側への依存がない（例: domain が `sqlalchemy` `httpx` `requests` `fastapi` `playwright` やinfrastructure 配下を import していない）
  - 例: `git diff --name-only <base>...HEAD | xargs grep -nE '^\s*(from|import) '` で洗い出し、レイヤー表と照合
- [ ] ビジネスルールが infrastructure / presentation に漏れていない（例: ルーターや DB リポジトリの中に URL 正規化やクロール可否判定が書かれている）
- [ ] ポートは内側（application/domain）で定義され、外側が実装している
- [ ] 外部ライブラリの型（ORMモデル、HTTPレスポンス型）がドメインの境界を越えて流れ込んでいない

frontend だけの変更なら、このステップは「対象外」と書いて飛ばす。

## Step 3. 基盤への影響・影響範囲

1. 変更ファイルを分類し、次に当たるものは **影響度: 高** として明示する。
   - ドメインモデル・共通ユーティリティ・基底クラス
   - DB スキーマ・マイグレーション
   - 設定・環境変数
   - 依存関係（`pyproject.toml` / `uv.lock` / `package.json` / lock ファイル）
   - `Dockerfile` / `compose.yaml` / CI 設定
2. 変更・削除された公開シンボル（関数・クラス・API エンドポイント・設定キー）ごとに、呼び出し元を `grep -rn` で数え、影響を受けるが diff に含まれていない箇所を列挙する。
3. シグネチャ・戻り値・例外・永続化形式の変更が後方互換を壊していないか。壊すなら設計書にその判断とロールバック方法があるか。
4. 結果を「影響度 高/中/低 と、その理由」で 1〜3 行にまとめる。

## Step 4. 過剰実装・過剰設計（/simplify 観点）

- [ ] 要求にない機能・オプション・設定項目・引数（誰も渡していないデフォルト引数を含む）
- [ ] 使われているのが1か所だけの抽象（ヘルパー、基底クラス、ジェネリクス、ファクトリ）
  - **例外**: レイヤー境界のポート（外部I/Oの差し替え口）は、実装が1つでもオニオン上の正当な抽象なので指摘しない。レイヤー内部の単一実装インターフェースは指摘する
- [ ] 起こり得ないケースのためのエラー処理・分岐・リトライ
- [ ] 標準ライブラリや既存コードにすでにあるものの再実装（重複）
- [ ] 同じ結果をより短く書ける箇所（「200行が50行になる」レベルのものに絞る。好みの問題は Nit 扱い）
- [ ] 明らかな非効率（ループ内の I/O、N+1 クエリ、不要な全件読み込み）

レビュー後に自動で簡素化したい場合は、メインのセッションで Claude Code 同梱の `/simplify` を実行するよう報告の最後で案内する（`/simplify` はコードを書き換えるので、このレビュー内では使わない）。

## Step 5. テストの合理性

### 5-1. red 先行か
次のどれかで確認する（上から順に試す）。
1. **コミット順**: `git log --reverse --name-only <base>..HEAD` で、テストが実装より先か同じタイミングで入っているか。
2. **設計書の実装ログ**: red 確認の記録（失敗したテスト名と理由）があるか。
3. **実地確認**（1・2で確認できないとき）:
   ```bash
   git worktree add /tmp/second-review-base <base>
   # 追加・変更されたテストファイルだけを /tmp/second-review-base にコピーして実行
   ```
   - 新しいテストが base で **失敗** すれば red 先行と整合する
   - base でも **通る** テストは変更を検証していない → Major として指摘
   - 失敗理由が ImportError だけのもの（新モジュール）は「弱い red」と注記する
   - 終わったら `git worktree remove /tmp/second-review-base`（削除できない環境ならその旨を報告）

### 5-2. テストの中身
- [ ] 設計書の成功条件それぞれにテストがある
- [ ] 実装の内部ではなく振る舞いを検証している
- [ ] モックはレイヤー境界（ポート）だけ。モック自体の動きを検証しているだけのテストがない
- [ ] 外部ネットワーク（実サイト）に依存しない。時刻・乱数・並行性は固定されている
- [ ] 境界値・異常系が設計の範囲で押さえられている（範囲外の網羅を求めるのは過剰なので指摘しない）

### 5-3. green の確認
プロジェクトの設定に従い実行する（`uv.lock` があれば `uv run` を付ける）: `ruff format --check .` / `ruff check .` / `mypy .` / `pytest`。frontend は `frontend/` で `npx biome ci .`（書き換えなし）と、`package.json` にあれば typecheck / test スクリプト。
Biome の設定（`biome.json`）で、diff の中でルールを無効化したり、`biome-ignore` コメントを追加したりしている箇所は理由を確認し、理由がなければ指摘する。結果を pass/fail で記録する。

## Step 6. 報告

以下の形式で返す。

```markdown
## 二次レビュー結果: <Approve | 要修正 | 要議論>
比較元: <base> / 対象: <n> ファイル / 設計書: <パス or なし>

### サマリー
- 影響度: 高/中/低 — <理由1行>
- 機械チェック: ruff format ✅ / ruff check ✅ / mypy ✅ / pytest ✅ / biome ci ✅（typecheck・test: …）
- red 先行: 確認済み / 一部未確認 / 確認できず — <方法>

### 指摘
| # | 重大度 | 観点 | 場所 | 指摘 | 根拠 | 提案 |
|---|---|---|---|---|---|---|
| 1 | Blocker | オニオン | backend/.../x.py:12 | … | … | … |

重大度: Blocker（マージ不可）/ Major（直すべき）/ Minor（直した方がよい）/ Nit（好み）

### 良かった点（1〜3個）

### 次の一手
- 指摘の修正は実装側で行う。簡素化の自動適用はメインのセッションで `/simplify`。
```

判定基準: Blocker が1つでもあれば「要修正」。設計判断そのものに疑問がある場合は「要議論」。
