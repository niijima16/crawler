# Pickup Assistant

商品を検索し、選んだ支払方法で**注文確認画面まで**自動で進めるツール。お気に入りに入れた商品が可能になったら、1分ごとの監視と毎晩21時（JST）の確認で検知し、自動の結果を通知する。

- `backend/`: FastAPI（Python）。API・監視ユースケース・ワーカー
- `frontend/`: React + Vite + TypeScript（nginx で配信）
- `compose.yaml`: ローカル起動用（`dynamodb` / `backend` / `worker` / `frontend`）

## ローカルで起動する

### 必要なもの
- Docker（Docker Compose v2）

Node や Python をローカルに入れる必要はない（ビルドも Docker の中で行う）。

### 1. 起動の準備（ローカルでは、何も設定しなくてよい）

```bash
cp .env.dollyteria .env   # 設定を変えたいときだけ（なくても起動できる）
```

サイトのパスワードを暗号化する鍵（`CREDENTIALS_KEY`）は、**ローカルでは空のままでよい**。初回の起動時に自動で作られ、Docker のボリュームに保存される（`backend` と `worker` で共有。保存したデータと同じ寿命）。AWS などの設定は要らない。

自分で鍵を指定したいときだけ、`.env` の `CREDENTIALS_KEY` に次のどちらかで作った値を入れる（指定があれば、そちらが優先される）。

```bash
openssl rand -base64 32 | tr '+/' '-_'
# または
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

> `.env` はコミットしない（`.gitignore` 済み）。自動生成の鍵は、データと同じ場所に置かれるため、**ローカル専用**。AWS などで動かすときは、必ず環境変数（や KMS）で鍵を指定する。

### 2. 起動する

```bash
docker compose up --build
```

初回はイメージのビルドに数分かかる。バックグラウンドで動かすときは `-d` を付ける。

起動したら、ブラウザで **http://127.0.0.1:8080** を開く（このPCからのみアクセスできる）。

### 3. 使い方

1. 「商品を探す」タブの **アカウント** カードで、サイトのメールアドレスとパスワードを入れて追加する（ログインできることを確認して、暗号化して保存する）。
2. **オプション** カードで、実行モード・支払方法・検索方式を選ぶ。
3. 商品を **コード**（商品 ID。`815572` や `product/815572`）または **部分一致** で探し、「この商品を選ぶ」。
4. **ご注文内容** カードの「確認画面まで進める」を押す。サイトが混雑しているときは、自動で再試行し、複数のセッションで通過を試みる。
5. ☆ を押すとお気に入りに登録される。可能になると自動で注文確定まで進む（同意の表示あり）。結果は「自動」タブに通知される。

### 3-1. ブラウザでする（確認画面を引き継ぐ）

実行モードの「ブラウザで」を選ぶと、ツールは確認画面まで進め、そのセッションをあなたのブラウザに渡す。あなたはブラウザで「する」を自分で押す（reCAPTCHA はそのブラウザで正規に動く）。ツールは「する」を押さない。

1クリックで開くには、同梱のブラウザ拡張を読み込む（任意。無くても DevTools 手動で進められる）。

```
chrome://extensions → デベロッパーモード → パッケージ化されていない拡張機能を読み込む → browser-extension/ を選ぶ
```

"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 --user-data-dir="$HOME/.pickup-chrome"

拡張の詳細は `browser-extension/README.md` を参照。クレジットカードは「ブラウザで」を選べない（確認画面まで自動で進めないため）。

### 3-2. キーワードお気に入り（新着を検知して確認画面に引き継ぐ）

「お気に入り」タブの「キーワードお気に入り」で、キーワード（部分一致）とジャンル（既定「SuperDollfie > 本体」）を登録すると、1分ごとと毎晩21時（JST）に、そのジャンルで新しく出てきた可能な商品を検知し、「自動」タブに通知する。通知の「確認画面を開く」で、その商品を確認画面まで進めてブラウザに引き継ぐ（拡張があれば自動で開く）。最後の「する」はブラウザで手動。

- 登録後の最初の監視で、今ある可能な一致商品も1回ずつ通知する。その後は新しく出たものが対象（同じ商品の重複通知はしない）。
- 「自動」タブの通知は、1件ずつ（「削除」）と、まとめて（「すべて削除」→「削除する」）削除できる。消しても、同じ商品がもう一度通知されることはない。
- 監視は検知・通知のみで、はしない（サーバー側の自動は未対応）。1アカウント10件まで。
- クレジットカードは選べない（確認画面まで進めないため）。
- ジャンルはサイトの全カテゴリから選べる（起動時に取得してキャッシュ。`CATEGORY_CACHE_TTL_SECONDS` 既定3600秒。取得失敗時は既定8件にフォールバック）。
- **自動で開く（任意）**: 「自動」タブの「新着通知で自動で確認画面を開く」を ON にすると（既定 OFF。このブラウザに保存）、新着通知が届いたら（画面を開いたときの未読も）自動で引き継ぎを始める。通知は1秒ごとに確認する（ツール画面を開いたままにしておく）。
  - 自動で開いた引き継ぎは、進捗のダイアログを出さない。結果はスイッチの下に1行だけ出る（引き継ぎ中〔やり直し回数・順番待ちの件数〕／確認画面を開いた／売り切れ／失敗）。
  - 同時に動かす引き継ぎは1件だけ（ブラウザはサイトのセッションを1つしか持てないため）。ほかは順番待ち（新しい順）。確認画面まで届いた・売り切れ・失敗のどれでも、すぐ次へ進む。**次の引き継ぎが確認画面まで届くと、前に開いた確認画面は使えなくなることがある**（ブラウザのセッションが置き換わるため）。
  - 自動で開いた引き継ぎは、1つのセッションで最大10分、失敗したステップだけを 0〜0.5秒の間隔でやり直す（ログインからやり直さない）。それでも混雑（時間切れ・上流エラー）で終わったら、0〜0.5秒待ってログインからやり直す。**売り切れるまで**続く（止めるときはスイッチを OFF。実行中の引き継ぎも止まる）。
  - 「する」は押さない（ブラウザで手動）。

### 3-3. 引き継ぎの進捗表示（リアルタイム）

「確認画面を開く」「確認画面まで進めてブラウザに引き継ぐ」を押すと、ログイン→カート→配送→確認画面→引き継ぎ の各ステップが、サーバーからの SSE（`GET /api/store-pickup-preview/stream`）でリアルタイムに表示される。混雑時の再試行は「再試行 N」と出る。完了すると拡張が確認画面を別タブで開く（拡張が無ければその旨を案内）。

- 21時の混雑で、開いた確認画面が 503 のときは、**拡張がそのタブを自動で再読み込み**する（間隔 約0.1〜0.6秒・開始から約3分まで）。3分で開けないときは手動「再試行」ボタン。再読み込みは GET のみで、同意チェック・ボタンの操作はしない。

### 3-4. 同意チェックを自動で入れる（任意）

`AUTO_CONSENT_CDP_URL` を設定すると、「確認画面を開く」の引き継ぎを始めたときに backend がホストの Chrome に CDP（9222番）で接続し、拡張が新しく開いた確認画面のタブで同意チェックを入れる（「する」は押さない）。引き継ぎが失敗したら中止する。既定は無効。

1. `.env` に次を書き、`docker compose up --build` で起動し直す

   ```
   AUTO_CONSENT_CDP_URL=http://host.docker.internal:9222
   ```

2. （うまく起動しないときだけ）開いている Chrome を ⌘Q で完全に終了する。手順3は専用プロファイルを使うので、普段の Chrome が動いていても別の Chrome として起動する。9222番が開かないときは、終了してからやり直す
3. ターミナルから、リモートデバッグ付きで起動する（このターミナルは開いたままにする）

   ```bash
   "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
     --remote-debugging-port=9222 --user-data-dir="$HOME/.pickup-chrome"
   ```

   別のターミナルで `curl http://localhost:9222/json/version` を実行し、JSON が返れば起動できている。
4. 初回だけ、**この Chrome で** `chrome://extensions` → デベロッパーモード → パッケージ化されていない拡張機能を読み込む → `browser-extension/` を選ぶ（専用プロファイルに保存されるので、2回目からは不要）
5. **手順3で開いた Chrome で** `http://127.0.0.1:8080` を開き、「確認画面を開く」を押す

- 結果は `docker compose logs backend` で確認する（成功: 「確認画面に同意チェックを入れた」、失敗: 「同意チェックの自動入力に失敗した」と理由）。
- Chrome 136 以降は、既定のプロファイル（普段使いの Chrome）ではリモートデバッグが効かない（セキュリティ対策）。そのため `--user-data-dir` で専用のプロファイルを指定する。
- 起動した後は、普段の Chrome を一緒に開いてよい。プロファイル（Cookie・ログイン・拡張）は別で、拡張と同意チェックが触るのは手順3の Chrome だけ。Dock にアイコンが2つ並ぶので、確認画面は手順3の Chrome で操作する。手順3の Chrome（とターミナル）を閉じると、引き継ぎと同意チェックは動かない。
- 普段の Chrome で同じアカウントのまま dollyteria にログインすると、サイトの仕様によっては片方のログインが切れるかもしれない（未確認）。21時の前後は、普段の Chrome でこのサイトを開かないほうが安全。
- macOS の Docker Desktop が前提（コンテナから `host.docker.internal` でホストに届く）。
- 手動で動かすスクリプト `backend/global_utils/playwright_sample.py` も残している（常駐して、開いた確認画面を処理する）。

### 4. 止める・初期化する

```bash
docker compose down        # 停止（保存したアカウント・お気に入りは残る）
docker compose down -v     # 停止して、保存したデータ（アカウント・お気に入り・自動生成した鍵）も消す
```

自分で指定した鍵（`CREDENTIALS_KEY`）を変えたときは、`down -v` でデータを消してから起動する（古い鍵で暗号化したアカウントは読めなくなる）。

### ログを見る

```bash
docker compose logs -f backend
docker compose logs -f worker     # 1分ごとの監視・21時の確認
```

## 設定（環境変数。`.env` で上書きする）

| 名前 | 既定 | 内容 |
|---|---|---|
| `CREDENTIALS_KEY` | 空（ローカルは自動生成） | サイトのパスワードを暗号化する鍵。AWS などでは必ず指定する |
| `ALLOW_ORDER_SUBMIT` | `false` | `true` のときだけ、注文確定と自動を許可する |
| `PREVIEW_PARALLELISM` | `3`（上限5） | 確認画面まで進めるときの同時セッション数 |
| `PREVIEW_DEADLINE_SECONDS` | `60`（上限120） | 確認画面までの制限時間（秒） |
| `TICK_DEADLINE_SECONDS` | `20` | 1分ごとの監視でするときの制限時間（秒） |
| `NIGHTLY_PARALLELISM` | `10`（上限10） | **21時の夜間チェックだけ**の同時セッション数 |
| `NIGHTLY_RETRY_INTERVAL_SECONDS` | `0.1` | 夜間チェックの503時の再試行間隔（秒）。待ち時間を伸ばさず素早く再試行する |
| `AUTO_CONSENT_CDP_URL` | 空（無効） | 引き継ぎ時に同意チェックを自動で入れる Chrome の CDP の URL（例: `http://host.docker.internal:9222`。3-4 参照） |

## 注意

- **注文確定は既定で無効**（`ALLOW_ORDER_SUBMIT=false`）。有効にすると、自動が実際に「する」を送る。取り消しにくい操作なので、内容を理解したうえで有効にする。
- サイトは、注文確定のボタンに reCAPTCHA を使っている。このツールは reCAPTCHA を回避しないため、**注文確定は現状では受理されない**見込み（結果は「受理されず」と通知される）。確認画面までは進める。
- サイトのパスワードは、サーバー側で暗号化して保存する。**このアプリには認証が無い**ため、公開しない（画面は `127.0.0.1` のみで待ち受ける）。
- 自動アクセスは、サイトの利用規約と負荷に配慮して使う。同時セッションと再試行には上限がある。
- **21時の夜間チェックは、混雑対策で既定10セッション・約0.1秒間隔の速い再試行**にしている（夜間のみ。手動実行・1分ごとの監視は従来どおり）。混雑時は毎秒数十〜百リクエスト規模になり、レート制限でアカウント/IP が弾かれる可能性がある。弾かれる場合は `NIGHTLY_PARALLELISM` を下げる・`NIGHTLY_RETRY_INTERVAL_SECONDS` を上げる。制限時間（`PREVIEW_DEADLINE_SECONDS`）で総量に上限が掛かる。

## 開発

テストは実サイトにアクセスしない（記録済みの HTML を使う）。

```bash
# backend
cd backend
uv run ruff format . && uv run ruff check . && uv run mypy . && uv run pytest

# DynamoDB Local でもリポジトリの契約テストを実行する（localhost を使う。127.0.0.1 は不可）
docker run -d --name ddb-test -p 8001:8000 amazon/dynamodb-local -jar DynamoDBLocal.jar -inMemory
DYNAMODB_ENDPOINT=http://localhost:8001 uv run pytest
docker rm -f ddb-test

# frontend（Biome・型・テストを Docker で実行）
docker build --target check ./frontend
```

- 構成のルールと作業の進め方は `CLAUDE.md`、設計書は `docs/design/`（`.gitignore` で git の対象外）を参照。
- `backend` の構成は、オニオン（`domain` / `application` / `infrastructure` / `presentation`）。
